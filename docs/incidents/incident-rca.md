# Controlled incident verification

All scenarios run in a dedicated PostgreSQL `_test` database through tests. There are no public incident-injection endpoints. Run `npm test` after the documented test database setup. The actual run and query plan are recorded under `docs/evidence/`.

| Incident | Controlled reproduction / inspected data | Corrective behavior and regression | Prevention |
|---|---|---|---|
| Overselling | Two independent API login sessions reserve a SKU with exactly one unit concurrently; inspect statuses, Inventory, Reservation and StockMovement. Initial implementation returned 500 for the losing request because raw Prisma SQLSTATE 40001 was not included in retry classification. | `repository.ts` handles ORM and raw-query serialization/deadlock errors. The capstone asserts one 201, one 409, one active reservation, nonnegative inventory, and ledger sums. | Conditional stock SQL, constraints, serializable transactions, deterministic lock ordering and bounded retries. |
| Stale stock | Populate Redis catalog cache, replay a cached query, receive three units and query again; also run the same expiry twice concurrently. Inspect cache headers and stock ledger. | Stock changes advance a database-scoped cache version. Expiry releases exactly once; cached stock changes from two to five units after receipt. | Fifteen-second cache TTL; authoritative PostgreSQL checks at checkout; retry-safe expiry sweep. |
| Payment/order mismatch | Send a signed event with the wrong amount, then fail a payment and send a delayed success. Inspect payment/order states and sale movements. | Amount mismatch returns 422. Failed reservation is released; delayed success creates no sale and is compensated to LATE_REFUNDED. | Event signature/amount validation, order lock, transactional event journal and stable compensation key. |
| Slow product search | Run `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` for the actual ILIKE pattern; inspect PostgreSQL indexes and the result limit. | Trigram GIN indexes and bounded pagination are installed. Price sorting uses SQL MIN over the entire filtered set before LIMIT/OFFSET. The captured plan is evidence, not a large-scale performance guarantee. | Review measured plans as the catalog grows; keep filtering in SQL and cache by query/version. A small synthetic dataset may correctly choose a sequential scan. |
| Failed shipping callback | Record FAILED on the first partial shipment, replay it, then apply a later DELIVERED event and finish the second shipment. Inspect ShippingEvent and OrderItem quantities. | Duplicate callback acknowledged once; later valid delivery recovers; over-fulfillment returns 409; order becomes DELIVERED only after all allocated units are delivered. | Signed callbacks, unique events, warehouse allocation checks, transition validation, audited recovery. |
| Duplicate refund | Receive one unit of a delivered two-unit line, issue its refund, replay the same signed refund event five times, then request refund again. Inspect Refund, FinancialMovement and StockMovement. | One refund record, one financial/commission reversal, one restock movement; replayed events return 200 and never repeat money/stock effects. | Unique constraints, cumulative exact integer allocation, order lock and provider idempotency key. |

External provider outages and public HTTPS hosting were not simulated as a successful external deployment. The optional Stripe adapter and deployment workflows require separate sandbox/hosting execution. Test output is retained without converting partial or simulated integrations into production claims.
