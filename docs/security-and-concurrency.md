# Security and concurrency decisions

Passwords are bcrypt hashes with cost 12. Access JWTs expire after 15 minutes and enforce HS256, issuer, audience, and an active database user on each authenticated request. Refresh JWT hashes are stored server-side, rotated transactionally with the old token's revocation, and grouped by family. Reuse revokes the family. Logout revokes refresh sessions; access tokens remain short-lived, with account suspension enforced immediately by the database lookup.

The refresh cookie is HttpOnly and SameSite=Strict, with Secure enabled in production. Refresh requires the exact trusted Origin; authenticated writes use an Authorization header. Cross-origin writes are rejected, CORS allows only the configured storefront, and Helmet and rate limits apply. Public registration accepts only CUSTOMER or SELLER; sellers begin pending. Privileged roles cannot be self-assigned. Seller products, stock, financial records, and relevant order lines are scoped by seller ID. Customers cannot read another customer's order. Prisma and tagged SQL parameterization protect search and writes.

Product uploads accept only JPEG, PNG, or WebP up to 5 MB, verify magic bytes, decode with a 25-million-pixel ceiling, remove metadata through re-encoding to WebP, and use random object keys. SVG and executable uploads are rejected. Uploaded original filenames never become object paths.

All monetary authority uses integer paise. Python's exact integer calculations allocate promotion remainders deterministically so the sum of per-line discounts equals the order discount. The transaction revalidates the cart, seller approval, product status, prices, commission rates, coupon validity and single-use claim. Each order line snapshots unit price, allocated discount, and commission.

Inventory obeys `0 <= reserved <= onHand`. Reservations use conditional SQL updates inside a serializable PostgreSQL transaction. Updates use deterministic lock ordering; serialization failures (`P2034` and raw-query SQLSTATE 40001/40P01) retry with a bounded backoff. Exactly one last-item checkout commits. The loser re-reads current stock and receives HTTP 409 OUT_OF_STOCK. A stock ledger has unique movement keys and a database trigger preventing update/delete.

Payment handlers lock the order and store a unique event ID in the same transaction as the state change. A duplicate event cannot repeat stock consumption. Provider amount mismatches are rejected. Failed or expired checkout releases stock once. Delayed successful payments do not consume released inventory: they enter REFUND_REQUIRED and a stable provider idempotency key drives compensation. An outbox committed with the business write ensures queued actions survive an API restart; the worker also sweeps expired orders independently of job delivery.

Partial fulfillment is bounded both by remaining order quantities and the actual consumed warehouse allocation. Delivered shipment states cannot move backwards. Return requests cannot exceed purchased quantity across open and completed requests. Received returns restock once. A unique return-to-refund relationship, provider idempotency key, and unique refund event prevent duplicate refunds. FinancialMovement records preserve sales and commission reversals once per refund/order line, including refunds after a settlement record. Payout records remain simulated; unresolved returned lines are excluded from new automatic settlements.

Actual regression evidence is in `docs/evidence/capstone.json`, Vitest reports, and Playwright reports. This is an educational synthetic marketplace; no real funds or customer communications are processed. Optional Stripe test functionality is implemented but requires genuine test credentials and provider-side verification before an external integration can be claimed.
